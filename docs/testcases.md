# Test cases: inventory governance

[Overview](../README.md) · [Release notes](../RELEASE_NOTES.md) · [Journey](journey.md) · [Design](developers.md) · **Acceptance criteria** · [Demo](../demo/README.md) · [Structure diagram](../README.md#how-it-fits-together)

Each case number is a link to its test file. **`make check-cases` measures that correspondence**
(§M). The design is in [developers.md](developers.md).

**Nature of this document**: it restates §1 of the [design](developers.md) (inventory engine) as **verifiable acceptance criteria**.
The implementation aims to pass these tests. The targets are `pkg/inventory/*` and
`inventory/cmd/*`.
**Verified**: three-state reconciliation, confidence, review queue, review-finalize state machine, judgment persistence, finalize plan, handoff gate, edge reconciliation.
**Execution policy**: reconciliation, the state machine and the gates are pure logic and need nothing real; judgment persistence and row-level security are Postgres integration tests.

> Acceptance criteria for **the parts pqcota implements**, such as ingestion, history, retention and asset scope, are in
> [pqcota inventory test cases](https://github.com/randyinthedev-hash/pqcota/blob/v0.9.1/inventory/testcases.md).

### K. Prose boundary (`tools/checkprose`): the engine lives upstream

Measures the Korean of documents and screen texts. Its whole job is to block **a word once removed from coming back**.
What exists now is recorded per file in `baseline.tsv`, and **only increases** are blocked.

**The engine and its cases (IC-K1~18) moved to upstream pqcota `tools/checkprose` on 2026-09-17.** With the code
copied into each repository, a common fix such as covering HTML comments had to be matched across three places in the same commit, and which
copy was the original became a licensing question. This repository keeps only the configuration: `rules.tsv` (what to block; words specific to this repository such as "gate" (`게이트`)

runs it with this configuration (`PROSE_CHECKER`). The case gate (IC-M8) measures nothing here because this section has no numbers.

### B. Language pairs (`tools/checklang`) ✅

The two public site pages (`docs/*.html`) write each text twice and hide one side with two CSS lines. This
approach creates **breakage that looks fine when viewed in one language**. There were nine places where `<span lang="ko">` was not
closed; with no closing tag, the parser put the following `<span lang="en">` inside it,
and when opened in English, hiding the outer Korean also hid the inner English, so six table headers and three table
cells became entirely blank. Viewed in Korean, all nine places looked fine.

**None of the four gates above caught it.** It came to light only on the day someone opened the site in English.
