# 설계 — 러너

고객 네트워크 안에서 도는 부분만 다룬다. 컨트롤 플레인 인프라는 여기 없다([README](README.md#여기-있는-것과-없는-것)).

---

## 1. 왜 러너인가

관측은 **고객 노드에서만** 된다 — `/proc`을 읽고, 실행 중 JVM에 attach하고, `AF_PACKET`으로
회선을 본다. 클라우드에서 손이 닿지 않는다. 그래서 세 가지 길이 있고, 둘은 막힌다.

| | 새로 만들 것 | 고객 방화벽 | SSH 키를 누가 갖나 | 프로비저닝 |
|---|---|---|---|---|
| 클라우드에서 직접 Ansible | 거의 없음 | **인바운드 개방** | **우리** | 됨 |
| **러너를 고객망에** | 통신 경로 하나 | 아웃바운드만 | 고객 | 됨 |
| 결과만 올리기 | 수신 API | 아웃바운드만 | 해당 없음 | **안 됨** |

**첫 번째가 막히는 이유** — 우리가 보관하게 되는 것은 고객 운영 서버의 셸 접근이다. collector는
`CAP_NET_RAW`와 프로세스 attach를, 프로비저닝은 파일 쓰기와 서비스 재시작을 요구한다.
**우리가 뚫리면 모든 고객이 함께 뚫린다.** 암호 인벤토리보다 이쪽이 값진 표적이다.
pqcota가 규정으로 세운 *"레거시 호스트에 실행체 투입 = RCE 대칭성"*이 그대로 적용된다.

**세 번째가 막히는 이유** — 관측만 받으면 적용·되돌림을 고객이 따로 해야 한다. 제품의 절반이 빠진다.

> **컨트롤 플레인은 기본적으로 호스팅된다.** 자기 환경에 두기를 원하는 조직에는 같은 컨테이너를
> 그대로 세운다 — 러너와 프로토콜은 어느 쪽이든 같다. 이 문서가 다루는 것도 그래서 러너뿐이다.

## 2. 러너가 하는 일

지금 데모의 `pqcota-ctl`과 같다. 새로 붙는 것은 **바깥과 이야기하는 입** 하나뿐이다.

```
[컨트롤 플레인]  계획 · 리뷰 · 확정 · 인벤토리 · 리포트
      │ ▲
 작업 │ │ 결과        둘 다 고객이 밖으로 연 HTTPS. 인바운드 없음
      ▼ │
[고객망]  러너 ──SSH──▶ 노드들 (collector 반입·실행·회수 / 플레이북 적용·되돌림)
```

**상태를 갖지 않는다.** 죽으면 다시 띄우면 그만이고, 데이터는 컨트롤 플레인에 있다.

## 3. 두 가지 포장

고객이 준비하는 것을 최소로 둔다. 어느 쪽이든 하는 일은 같다.

**① 이미 돌리는 Ansible에 잡 하나** — 이 제품을 사려는 조직은 대개 Ansible(AWX·Tower)을 이미
운영하고, 그 절차는 이미 승인돼 있다. 새 서버도 상주 프로세스도 없다.

**② 컨테이너 하나** — Ansible이 없는 조직용.

```bash
docker run -d --restart=always \
  -e PQCATON_ORG=<조직> -e PQCATON_TOKEN=<발급 토큰> \
  <이미지>
```

## 4. 밖으로 보내는 것과 보내지 않는 것

**이 절이 이 문서에서 가장 중요하다.** 고객 보안팀이 먼저 볼 자리다.

| 보낸다 | 보내지 않는다 |
|---|---|
| 관측 결과(`CollectionResult`) — 어떤 노드가 어떤 암호 자산을 쓰는가 | **SSH 키·비밀번호** — 러너 안에 남는다 |
| 관측된 통신 엣지와 협상 결과 | **파일 내용** — 설정 파일 원문을 읽어 보내지 않는다 |
| 완전성 맵 — 무엇을 관측하지 못했는가 | **패킷 페이로드** — 핸드셰이크의 협상 그룹만 본다. 복호화하지 않는다 |
| 러너 상태(버전·마지막 실행) | **애플리케이션 데이터** |

접근 비밀은 pqcota의 계약 타입에 **필드 자체가 없어** 담을 방법이 없다. 설계가 아니라 스키마가 막는다.

## 5. 지금 없는 것

| | |
|---|---|
| 러너 | **없다.** 데모의 `pqcota-ctl`이 SSH 쪽 일을 이미 하지만, 바깥과 이야기하지 않는다 |
| 작업 배포·결과 수신 프로토콜 | **없다.** 지금 `pqcota-ingest`는 디렉터리에서 파일을 읽고 `PQCOTA_DSN`으로 Postgres에 쓴다 — 이미 네트워크를 넘지만 **DB 연결이지 검증 경계가 아니다**(아래) |
| 발신자 인증 | **재료는 있다** — collector가 결과에 ed25519 서명을 붙이고(`pqcota-keygen`), 중앙이 공개키로 검증하게 pqcota가 이미 설계했다. 조직마다 공개키를 등록하면 그대로 쓴다 |
| 사용자 인증·권한 | 없다 |
| 화면 | 없다. 지금은 CLI 텍스트 |

### 5.1 왜 DB에 직접 붙이지 않나

`pqcota-ingest`가 이미 원격 Postgres에 쓸 수 있으니, 러너에 DSN을 주면 코드 없이 적재가 된다.
**컨트롤 플레인이 고객 환경에 있을 때는 실제로 그렇게 한다** — 새로 만들 것이 없다.

호스팅에서는 그 경로를 쓰지 않는다. 러너가 우리 DB에 직접 붙는 형태가 되기 때문이다.

| | |
|---|---|
| DB를 인터넷에 연다 | Postgres는 그런 노출을 전제로 만들어지지 않았다 |
| 자격증명을 고객마다 배포 | 하나가 새면 그 계정으로 무엇을 할 수 있는지가 문제가 된다 |
| 검증 계층이 없다 | 감염된 러너가 임의의 행을 쓴다. **조직 격리가 DB 권한에만 의존**하게 된다 |
| 서명을 못 본다 | ed25519 검증이 클라이언트 쪽이 되어 의미가 없어진다 |
| 스키마가 묶인다 | 모든 러너가 DB 스키마 버전에 붙는다. 업그레이드가 전 고객 동시 작업이 된다 |

수신 API가 필요한 이유는 "네트워크를 넘어서"가 아니라 **검증·권한·버전의 경계**를 두기
위해서다. 그 경계에서 서명을 확인하고, 조직을 붙이고, 스키마 차이를 흡수한다.

## 6. 러너 프로토콜

§5.1이 정한 경계의 일 — **서명 확인 · 조직 부여 · 스키마 흡수** — 가 그대로 이 API의 일이다.
여기에 작업 배포가 얹힌다.

### 6.1 원칙 넷

**아웃바운드만.** 러너가 묻고 컨트롤 플레인이 답한다. 반대 방향의 연결은 없다 — 그래서
고객 방화벽에 예외가 필요 없다.

**러너는 상태를 갖지 않는다.** 죽으면 다시 띄우면 그만이다. 진행 중이던 작업은 만료되어
다시 배포된다.

**실패를 숨기지 않는다.** 관측이 안 됐으면 안 됐다고 올린다. 조용히 빠지면 중앙에서
"그 노드엔 없다"로 읽힌다 — pqcota가 종료코드를 0으로 두는 것과 같은 이유다.

**서명 없는 결과는 받지 않는다.** 다만 **거절된 사실은 남긴다.** 조용히 버리면 러너가
잘못 설정된 것과 아무 일도 없던 것이 구분되지 않는다.

### 6.2 엔드포인트 넷

```
POST /v1/runner/register    러너 등록 — 조직 토큰 + collector 공개키
GET  /v1/runner/jobs        할 일을 받아간다 (롱폴)
POST /v1/runner/results     관측 결과·적용 결과를 올린다
POST /v1/runner/status      살아 있음 · 버전 · 마지막 실행
```

**작업(job)은 두 가지뿐이다.**

| kind | 러너가 하는 일 | 돌려주는 것 |
|---|---|---|
| `observe` | collector를 대상 노드에 반입·실행·회수 | `CollectionResult[]` |
| `provision` | 받은 플레이북을 자기 Ansible로 적용 또는 되돌림 | 실행 결과 + before 캡처 |

`provision` 작업은 **확정된 계획에서만** 나온다. 컨트롤 플레인이 그 게이트를 지키므로
러너는 받은 것을 돌릴 뿐 판단하지 않는다.

### 6.3 무엇으로 신뢰하나

두 층이다.

| 층 | 무엇을 확인 | 없으면 |
|---|---|---|
| **러너 토큰** | 이 러너가 그 조직의 것인가 | 요청 거절 |
| **collector ed25519 서명** | 이 관측이 진짜 그 collector가 낸 것인가 | 결과 거절 — 기록은 남긴다 |

**토큰만으로는 부족하다.** 러너가 감염되면 토큰도 함께 넘어간다. collector 서명은 그 아래
층이라, 러너를 잡아도 관측을 위조하려면 collector 키가 따로 필요하다.

서명은 새로 만들 것이 아니다 — pqcota가 이미 `pqcota-keygen`으로 키쌍을 만들고
`PQCOTA_SIGN_KEY`로 서명한다. 조직마다 공개키를 등록해 두면 그대로 쓴다.

### 6.4 중복과 순서

같은 결과가 두 번 올 수 있다 — 러너가 올린 뒤 응답을 못 받고 재시도하는 경우다.
**인벤토리가 append-only라 중복이 이력을 망가뜨리지는 않지만**, 같은 관측이 두 번 쌓이면
"언제 봤나"가 틀어진다.

`Envelope`의 `collector_id` + `target_node_id` + 수집 시각이 그 자리에서 중복 키가 된다.
같은 키가 다시 오면 새로 쌓지 않고 받았다고만 답한다.

### 6.5 버전이 어긋날 때

러너는 자동으로 갱신되지만 즉시는 아니다. **옛 러너가 새 컨트롤 플레인에 붙는 구간이 늘 있다.**

- 계약(`contracts/`)이 순수 additive로만 바뀌므로 옛 러너가 보낸 것은 그대로 읽힌다
- 컨트롤 플레인이 옛 러너가 모르는 작업을 주지 않는다 — `register`에서 받은 러너 버전으로 거른다
- 너무 오래된 러너는 갱신을 요구하고 작업을 주지 않는다. **그 사실을 상태로 남긴다** — 조용히
  일을 안 하면 "관측할 것이 없다"로 읽힌다

### 6.6 지금 없는 것

이 절 전부. 설계이고 구현은 없다.

## 7. 이식성 — 깨지 않아야 할 것

컨트롤 플레인은 **컨테이너 + 관리형 PostgreSQL + S3 호환 스토리지**만 쓴다. 제공사 전용
서비스(전용 서버리스·큐·인증·워크플로)를 쓰지 않는다.

이유는 취향이 아니다. **어디서 돌릴지가 고객마다 다르다** — 우리 호스팅, 고객이 지정한
클라우드, 고객 자기 환경. 셋 다 같은 컨테이너여야 한다. 그때 며칠 안에 세울 수 있어야
그 요구를 받는다.

**지금 코드가 이미 그 조건을 만족한다** — Go 정적 바이너리와 `pgxpool`뿐, 클라우드 SDK가 하나도
없다. 지키는 것이 만드는 것보다 쉽다.
