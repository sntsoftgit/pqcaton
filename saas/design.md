# 설계 — 러너

고객 네트워크 안에서 도는 부분만 다룹니다. 컨트롤 플레인 인프라는 여기 없습니다([README](README.md#여기-있는-것과-없는-것)).

---

## 1. 왜 러너인가

관측은 **고객 노드에서만** 됩니다 — `/proc`을 읽고, 실행 중 JVM에 attach하고, `AF_PACKET`으로
회선을 봅니다. 클라우드에서 손이 닿지 않습니다. 그래서 세 가지 길이 있고, 둘은 막힙니다.

| | 새로 만들 것 | 고객 방화벽 | SSH 키를 누가 갖나 | 프로비저닝 |
|---|---|---|---|---|
| 클라우드에서 직접 Ansible | 거의 없음 | **인바운드 개방** | **우리** | 됨 |
| **러너를 고객망에** | 통신 경로 하나 | 아웃바운드만 | 고객 | 됨 |
| 결과만 올리기 | 수신 API | 아웃바운드만 | 해당 없음 | **안 됨** |

**첫 번째가 막히는 이유** — 우리가 보관하게 되는 것은 고객 운영 서버의 셸 접근입니다. collector는
`CAP_NET_RAW`와 프로세스 attach를, 프로비저닝은 파일 쓰기와 서비스 재시작을 요구합니다.
**우리가 뚫리면 모든 고객이 함께 뚫립니다.** 암호 인벤토리보다 이쪽이 값진 표적입니다.
pqcota가 규정으로 세운 *"레거시 호스트에 실행체 투입 = RCE 대칭성"*이 그대로 적용됩니다.

**세 번째가 막히는 이유** — 관측만 받으면 적용·되돌림을 고객이 따로 해야 합니다. 제품의 절반이
빠집니다.

> **컨트롤 플레인은 기본적으로 호스팅됩니다.** 자기 환경에 두기를 원하는 조직에는 같은 컨테이너를
> 그대로 세웁니다 — 러너와 프로토콜은 어느 쪽이든 같습니다. 이 문서가 다루는 것도 그래서 러너뿐입니다.

## 2. 러너가 하는 일

지금 데모의 `pqcota-ctl`과 같습니다. 새로 붙는 것은 **바깥과 이야기하는 입** 하나뿐입니다.

```
[컨트롤 플레인]  계획 · 리뷰 · 확정 · 인벤토리 · 리포트
      │ ▲
 작업 │ │ 결과        둘 다 고객이 밖으로 연 HTTPS. 인바운드 없음
      ▼ │
[고객망]  러너 ──SSH──▶ 노드들 (collector 반입·실행·회수 / 플레이북 적용·되돌림)
```

**상태를 갖지 않습니다.** 죽으면 다시 띄우면 그만이고, 데이터는 컨트롤 플레인에 있습니다.

## 3. 두 가지 포장

고객이 준비하는 것을 최소로 둡니다. 어느 쪽이든 하는 일은 같습니다.

**① 이미 돌리는 Ansible에 잡 하나** — 이 제품을 사려는 조직은 대개 Ansible(AWX·Tower)을 이미
운영하고, 그 절차는 이미 승인돼 있습니다. 새 서버도 상주 프로세스도 없습니다.

**② 컨테이너 하나** — Ansible이 없는 조직용입니다.

```bash
docker run -d --restart=always \
  -e PQCATON_TOKEN=<발급 토큰> -e PQCATON_API=<컨트롤 플레인 주소> \
  <이미지>
```

**조직을 적는 자리가 없습니다.** 토큰에서 유도합니다(§6.4) — 적는 자리를 두면 러너가 자기
조직을 주장하는 길이 생기고, 그 순간 §6.4의 전제가 무너집니다.

## 4. 밖으로 보내는 것과 보내지 않는 것

**이 절이 이 문서에서 가장 중요합니다.** 고객 보안팀이 먼저 볼 자리입니다.

| 보낸다 | 보내지 않는다 |
|---|---|
| 관측 결과(`CollectionResult`) — 어떤 노드가 어떤 암호 자산을 쓰는가 | **접속 정보 일체** — 주소·포트·계정·키·비밀번호. 러너 설정에만 있습니다 |
| 관측된 통신 엣지와 협상 결과 | **파일 내용** — 설정 파일 원문을 읽어 보내지 않습니다 |
| 완전성 맵 — 무엇을 관측하지 못했는가 | **패킷 페이로드** — 핸드셰이크의 협상 그룹만 봅니다. 복호화하지 않습니다 |
| 러너 상태(버전·마지막 실행) | **애플리케이션 데이터** |

**주소는 기본적으로 올리지 않습니다.** 컨트롤 플레인이 갖는 것은 머신 지문과 표시이름이고,
작업 지시도 식별자로만 합니다 — 우리 DB가 털려도 고객 내부 주소 지도가 나오지 않습니다.
**다만 인벤토리 화면에서 주소를 보고 싶은 조직도 있어, 켜고 끄는 것은 고객이 정합니다**(§6.3.1).
그 설정은 러너에 있어 우리가 바꿀 수 없습니다.

**무엇이 무엇으로 막히는지**는 구분해 적습니다. 둘은 강도가 다르고, 같은 것처럼 적으면
약한 쪽이 실제보다 강하게 들립니다.

| 막히는 것 | 무엇이 막나 |
|---|---|
| **SSH 키·비밀번호** | **타입입니다.** pqcota의 `MachineEndpoint`에 비밀 필드가 아예 없습니다 — 인벤토리에 실리는 것은 `node_id`·이름·IP·포트뿐이라 담을 자리가 없습니다. 접속 정보는 실행에만 쓰고 영속하지 않습니다 |
| **파일 원문 · 패킷 페이로드** | **규약입니다.** `CollectionResult.raw_capture`는 자유형 `bytes`라 스키마가 막아 주지 않습니다. pqcota가 계약 주석에 *"여기에 설정 파일 원문·패킷 페이로드·자격증명을 담지 않는다"*를 명문화했고(v0.2.0), collector가 그것을 지킵니다 |

**규약은 타입보다 약합니다.** collector를 바꾸면 깨질 수 있는 약속이라, 수신 API가 한 겹 더
봅니다(§6.7). 고객 보안팀에는 이 차이를 그대로 말합니다 — "스키마가 막는다"고 뭉뚱그리면
나중에 한 줄이 틀린 것이 문서 전체의 신뢰를 깎습니다.

## 5. 지금 없는 것

| | |
|---|---|
| 러너 | **없습니다.** 데모의 `pqcota-ctl`이 SSH 쪽 일을 이미 하지만, 바깥과 이야기하지 않습니다 |
| 작업 배포·결과 수신 프로토콜 | **없습니다.** 지금 `pqcota-ingest`는 디렉터리에서 파일을 읽고 `PQCOTA_DSN`으로 Postgres에 씁니다 — 이미 네트워크를 넘지만 **DB 연결이지 검증 경계가 아닙니다**(아래) |
| 발신자 인증 | **적재 쪽은 pqcota v0.2.0에 있습니다** — 서명 필수 모드(`RequireSignature`), collector_id로 키를 찾아 그 키로만 확인하는 `sign.VerifyFrom`, 거절·미검증을 남기는 `pqcota_rejections`. **없는 것은 조직별 공개키 등록소**이고 그건 우리 쪽 일입니다(§6.4) |
| 사용자 인증·권한 | 없습니다 |
| 화면 | 없습니다. 지금은 CLI 텍스트입니다 |

> **조직 축은 pqcota v0.2.0에 들어갔습니다.** 인벤토리 전 테이블이 조직에 묶이고, 조직을 대지
> 않고 저장소를 열면 `PQCOTA_REQUIRE_ORG=1`에서 그 자리에서 에러가 납니다. 이건 컨트롤 플레인
> 쪽 이야기라 여기서는 더 다루지 않습니다 — **러너는 자기 조직을 토큰으로 말할 뿐, 저장될
> 조직을 정하지 않습니다.** 그건 수신 API가 토큰에서 붙입니다(§6.4).

### 5.1 왜 DB에 직접 붙이지 않나

`pqcota-ingest`가 이미 원격 Postgres에 쓸 수 있으니, 러너에 DSN을 주면 코드 없이 적재가 됩니다.
**컨트롤 플레인이 고객 환경에 있을 때는 실제로 그렇게 합니다** — 새로 만들 것이 없습니다.

호스팅에서는 그 경로를 쓰지 않습니다. 러너가 우리 DB에 직접 붙는 형태가 되기 때문입니다.

| | |
|---|---|
| DB를 인터넷에 연다 | Postgres는 그런 노출을 전제로 만들어지지 않았습니다 |
| 자격증명을 고객마다 배포 | 하나가 새면 그 계정으로 무엇을 할 수 있는지가 문제가 됩니다 |
| 검증 계층이 없다 | 감염된 러너가 임의의 행을 씁니다 |
| 조직을 러너가 고른다 | pqcota v0.2.0으로 조직 축이 코드에 생겼지만, **그 값을 정하는 쪽이 러너면 의미가 없습니다.** 조직은 러너가 주장하는 것이 아니라 토큰에서 유도되어야 합니다 |
| 서명을 못 본다 | ed25519 검증이 클라이언트 쪽이 되어 의미가 없어집니다 |
| 스키마가 묶인다 | 모든 러너가 DB 스키마 버전에 붙습니다. 업그레이드가 전 고객 동시 작업이 됩니다 |

수신 API가 필요한 이유는 "네트워크를 넘어서"가 아니라 **검증·권한·버전의 경계**를 두기
위해서입니다. 그 경계에서 서명을 확인하고, 조직을 붙이고, 스키마 차이를 흡수합니다.

## 6. 러너 프로토콜

§5.1이 정한 경계의 일 — **서명 확인 · 조직 부여 · 스키마 흡수** — 이 그대로 이 API의 일입니다.
여기에 작업 배포가 얹힙니다.

### 6.1 원칙 넷

**아웃바운드만.** 러너가 묻고 컨트롤 플레인이 답합니다. 반대 방향의 연결은 없습니다 — 그래서
고객 방화벽에 예외가 필요 없습니다.

**러너는 상태를 갖지 않습니다.** 죽으면 다시 띄우면 그만입니다. 진행 중이던 작업은 만료되어
다시 배포됩니다.

**실패를 숨기지 않습니다.** 관측이 안 됐으면 안 됐다고 올립니다. 조용히 빠지면 중앙에서
"그 노드엔 없다"로 읽힙니다 — pqcota가 종료코드를 0으로 두는 것과 같은 이유입니다.

**서명 없는 결과는 받지 않습니다.** 다만 **거절된 사실은 남깁니다.** 조용히 버리면 러너가
잘못 설정된 것과 아무 일도 없던 것이 구분되지 않습니다.

### 6.2 엔드포인트 넷

```
POST /v1/runner/register    러너 등록 — 조직 토큰과 러너 버전만
GET  /v1/runner/jobs        할 일을 받아간다 (롱폴)
POST /v1/runner/results     관측 결과·적용 결과를 올린다
POST /v1/runner/status      살아 있음 · 버전 · 마지막 실행
```

**`register`는 collector 공개키를 받지 않습니다.** 러너가 자기 키를 등록할 수 있으면
§6.4의 두 층이 한 층이 됩니다 — 러너를 잡은 쪽이 키쌍을 만들어 등록하고 그 키로 서명하면
됩니다. 토큰 하나로 둘 다 열립니다. 공개키 등록은 **관리자 콘솔 경로**로만 열고, 러너가
닿는 어떤 엔드포인트로도 열지 않습니다.

#### TLS는 앞에서 끊습니다

**러너가 거는 것은 HTTPS입니다.** 다만 그 TLS를 **애플리케이션이 직접 하지 않습니다** —
앞단(로드밸런서 또는 리버스 프록시)에서 끊고, 앱은 그 뒤에서 평문을 듣습니다.

| 왜 | |
|---|---|
| 설치형·전용 인스턴스 | 고객은 자기 프록시와 인증서 체계 뒤에 둡니다. 앱이 TLS를 강제하면 그 환경에 못 얹힙니다 |
| 상태 | 앱이 ACME를 돌면 인증서 갱신·저장 상태를 갖습니다. **컨트롤 플레인도 러너도 상태를 갖지 않는다**가 이 설계의 축인데 거기에 구멍이 납니다 |
| 운영 | 인증서 수명주기를 앱 밖으로 빼면 1인 운영에서 장애 지점이 하나 줍니다 |

**그래서 배포 요건이 생깁니다. 「그럴 것이다」로 두지 않습니다.**

| | |
|---|---|
| 앱이 듣는 자리 | **프록시만 닿는 곳**에서 듣습니다. 평문 포트가 인터넷에 열리면 **러너 토큰이 `Authorization` 헤더로 그대로 샙니다** |
| 프록시 헤더 | `X-Forwarded-Proto`를 **기본으로 믿지 않습니다.** 앞단이 있다고 설정으로 밝힌 배포에서만 봅니다 — 아무나 그 헤더를 붙일 수 있는 자리에서 믿으면 평문 요청이 HTTPS로 둔갑합니다 |
| 신뢰를 켰을 때 | `https`가 아닌 요청은 거절하고 **그 사실을 남깁니다.** 조용히 받으면 프록시 설정이 풀린 것을 아무도 모릅니다 |
| HSTS·인증서 | 앞단이 맡습니다 |

러너 쪽은 반대로 **평문으로 걸지 않습니다.** 아웃바운드 HTTPS만 씁니다(§6.1).

**작업(job)은 세 가지입니다.**

| kind | 러너가 하는 일 | 돌려주는 것 |
|---|---|---|
| `enroll` | 대상에 붙어 **머신 지문만** 확인 (§6.3) | `MachineIdentity` + 연결 성공·실패 사유 |
| `observe` | collector를 대상 노드에 반입·실행·회수 | `CollectionResult[]` |
| `provision` | 받은 플레이북을 자기 Ansible로 적용 또는 되돌림 | 실행 결과 + before 캡처 |

`provision` 작업은 **확정된 계획에서만** 나옵니다. 컨트롤 플레인이 그 게이트를 지키므로
러너는 받은 것을 돌릴 뿐 판단하지 않습니다.

#### 6.2.1 작업의 일생 — 만료와 재배포

러너는 상태를 갖지 않습니다(§6.1). 죽으면 다시 띄우면 그만이고, **진행 중이던 작업은
만료되어 다시 배포됩니다.** 그 "다시 배포"가 작업 종류마다 같으면 안 됩니다.

```
대기 ──받아감──▶ 점유(만료시각 있음) ──▶ 완료
                      │
                      └─ 만료 ──▶ ?   ← 여기가 종류마다 다르다
```

| kind | 만료되면 | 왜 |
|---|---|---|
| `enroll` · `observe` | **다시 대기로.** 자동 재배포 | 읽기입니다. 두 번 해도 대상이 바뀌지 않고, 결과가 겹쳐도 멱등이 접습니다(§6.5) |
| **`provision`** | **재배포하지 않습니다.** 「확인 필요」로 두고 사람에게 알립니다 | **쓰기입니다.** 러너가 플레이북을 이미 적용했는데 응답만 못 준 것일 수 있습니다. 다시 주면 **두 번 적용**되고, 두 번째 `before` 캡처는 **이미 바뀐 상태**를 찍어 되돌릴 근거가 망가집니다 |

**"두 번 적용해도 괜찮게 만들면 되지 않나"** — 플레이북은 대개 멱등하게 쓰지만, 우리가
그것을 **보장할 수는 없습니다.** 고객이 확정한 계획에서 나온 플레이북이고, 그 안에 무엇이
있는지는 계획이 정합니다. 보장할 수 없는 것을 전제로 자동 재실행을 걸지 않습니다.

**사람이 판단할 근거는 남아 있습니다** — 적용 전 상태 캡처와 실행 기록이 이미 저장되므로
(`pqcota_provisioning_record`), *"어디까지 됐나"*를 보고 다시 돌릴지 정할 수 있습니다.

**점유 만료 시간은 작업 종류가 정합니다.** 관측은 대상 수에 비례해 길어지고, 적용은
플레이북에 달렸습니다. 짧으면 멀쩡히 도는 작업을 뺏고, 길면 죽은 러너의 작업이 그만큼
묶입니다. 러너가 **진행 중임을 알리면 만료가 미뤄집니다** — 그래야 긴 작업에 억지로 큰
값을 잡지 않아도 됩니다.

#### 작업은 결과로 닫습니다

**작업을 닫는 엔드포인트를 따로 두지 않습니다.** 위 넷이 전부입니다 — 러너는 결과를 올리며
`job_id`와 `runner_id`를 함께 보내고, 컨트롤 플레인이 적재한 뒤 그 작업을 닫습니다.

| | |
|---|---|
| 왜 나누지 않나 | 적재와 닫기가 두 왕복이면 **"결과는 올렸는데 닫지 못한" 구간**이 생깁니다. 그 작업은 만료돼 한 번 더 배포되고, 관측은 멱등이 접지만 대상과 러너는 그만큼 더 일합니다 |
| 못 닫아도 | **결과를 버리지 않습니다.** 어긋난 것이 작업 id 하나인데 관측 전체를 잃습니다. 무엇이 어긋났는지는 응답에 담아 돌려주고(`closed`·`not-found`·`not-leased`), 적재는 그대로 둡니다 |
| 거절된 결과가 있어도 | **닫습니다.** 러너는 시킨 일을 했습니다. 서명이 맞지 않는 것은 다시 시킨다고 달라지지 않고(옛 collector는 같은 서명을 다시 만듭니다 — §6.6), 사유는 `pqcota_rejections`에 남습니다 |
| 적재가 실패하면 | **닫지 않습니다.** 러너가 다시 올리면 그때 닫히고, 러너가 죽으면 만료가 회수합니다. 적재되지 않은 것을 「끝났다」로 두는 편이 훨씬 나쁩니다 |

> **러너가 자기 id를 스스로 댑니다.** 토큰은 조직 단위라 `runner_id`를 토큰에서 유도할
> 수 없습니다. 같은 조직의 러너끼리는 서로의 작업을 닫을 수 있다는 뜻입니다 — 조직 경계는
> 서지만 조직 안은 아직 서지 않습니다. `register`(M5)가 러너를 토큰에 묶으면 그때 닫힙니다.

### 6.2.2 영역 — 러너 하나가 맡는 범위

**조직은 이관 영역을 여럿 둡니다.** 본사·DR 센터·지사처럼 망이 갈리면 한 러너가 전부에
닿지 못합니다. 그래서 **영역마다 러너를 하나씩** 놓고, 노드는 자기 영역에 속합니다.

```
조직 ──┬── 영역 "본사"   ── 러너 하나 ── 노드들
       └── 영역 "DR 센터" ── 러너 하나 ── 노드들
```

**영역을 러너와 따로 두는 이유** — 러너는 상태를 갖지 않고 죽으면 다시 뜹니다(§6.1).
노드를 러너에 직접 매면 러너를 갈아 끼울 때마다 그 관계가 끊깁니다. **러너는 갈리고
영역은 남습니다.** 같은 영역에 러너를 둘 띄워도 모델이 깨지지 않는 것도 같은 이유입니다 —
둘 다 그 영역의 노드에 닿으므로 어느 쪽이 작업을 가져가도 됩니다.

| 영역이 없으면 | |
|---|---|
| **작업이 닿지 않는 러너에게 갑니다** | 배포가 조직만 보고 고르면 DR 노드 작업을 본사 러너가 가져갑니다. 실패하고, 만료되고, 또 아무나 가져갑니다 |
| **감염된 러너의 반경이 조직 전체입니다** | 결과 검증이 조직까지만 보면, 한 영역의 러너가 **다른 영역 노드의 결과**를 지어내 올릴 수 있습니다. 영역이 있으면 거기서 한 겹 더 걸립니다 |
| **운영자가 러너를 골라야 합니다** | "이 노드는 어느 러너가 보나"를 사람이 기억하게 됩니다 |

**영역도 토큰이 정합니다.** 조직과 같은 이유입니다 — 러너가 자기 영역을 주장할 수 있으면
위의 두 번째 줄이 그대로 무너집니다.

```
pqcaton_zone
    org        TEXT NOT NULL
    id         TEXT NOT NULL        -- 조직 안에서 유일
    label      TEXT                 -- "본사", "DR 센터"
    PRIMARY KEY (org, id)

pqcaton_runner_token  … + zone TEXT NOT NULL   -- 토큰이 조직과 영역을 함께 정합니다
pqcaton_job           … + zone TEXT NOT NULL   -- 배포는 영역 안에서만
pqcaton_node_zone                              -- 등재가 만드는 행
    org        TEXT NOT NULL
    node_id    TEXT NOT NULL        -- 상류의 앵커(§1.4)
    zone       TEXT NOT NULL
    PRIMARY KEY (org, node_id)
```

#### 상류에는 영역이 없습니다. 그래서 옆에 둡니다

pqcota 계약에는 **러너도 영역도 없습니다**(proto 아홉 개에 `runner` 0건, `CollectRequest`는
`target_node_ids`뿐). 조직조차 계약이 아니라 저장 계층에만 있습니다.

**그것이 옳습니다.** 영역은 **배포 축이지 관측 사실이 아닙니다.** 어느 러너가 실행했는지는
관측 도구가 몰라도 되고, 계약에 넣으면 관측 데이터에 우리 배포 구조가 새어 들어갑니다.

| 방법 | |
|---|---|
| 상류 테이블에 컬럼을 더한다 | **안 합니다.** 상류 스키마를 우리가 고치면 업그레이드마다 부딪히고, 마감(2026-08-27)까지 상류에 새 요구를 넣지 않기로 했습니다 |
| 조직 문자열에 영역을 넣는다(`acme-dr`) | **안 합니다.** 조직 격리가 문자열 규칙이 되고, 과금·판정은 조직 단위인데 그것까지 갈립니다 |
| **우리 테이블에서 잇는다** | **이렇게 합니다.** `node_id`가 상류의 앵커라(§1.4 — `Envelope.target_node_id`와 같은 값) `(org, node_id) → zone` 한 장이면 됩니다. 상류 인벤토리는 영역을 모르고, 영역별 보기는 우리가 조인해 만듭니다 |

이 방향은 이 리포의 경계와 같습니다 — **우리가 상류를 부르지, 상류가 우리를 부르지
않습니다**([README](README.md#왜-별도-폴더인가)).

> **지금 없습니다.** 등재(M3)가 `pqcaton_node_zone`을 만드는 자리입니다 — 등재는 러너가
> 붙어 확인하는 것이라 그 사실이 그 순간 생깁니다. 지금은 저장할 자리가 없어 작업이
> 조직의 아무 러너에게나 나갑니다.

### 6.3 노드 등재 — 연결확인

관측 전에 한 단계를 둡니다. **운영자가 대상을 올리고 "연결확인"을 누르면, 러너가 붙어
머신 지문을 확인해 옵니다.** 그 뒤의 관측은 **등재된 노드에만** 갑니다.

pqcota가 이미 그 전제로 만들어져 있습니다 — `CollectRequest`는 *"스코프 마스터 게이트를
통과한 노드만"* 받고, 미등재 노드의 결과는 저장하지 않고 **등재 판정 요청**으로 셉니다
(§1.4 임의 수집 금지). 여기서 없던 것은 그 게이트를 **채우는 절차**였습니다.

```
운영자가 대상 등록 ──▶ [enroll] ──▶ 지문 확보 ──▶ 등재
                                                    │
                                     [observe]는 등재된 것에만 ◀┘
```

**접속 정보는 컨트롤 플레인에 올라오지 않습니다 — 주소도 포함해서입니다.**

| 어디에 | 무엇 |
|---|---|
| **러너(고객망)** | 대상 목록 전체 — **주소·포트·계정·키·비밀번호.** 고객이 러너 설정에 둡니다 |
| 컨트롤 플레인 | **머신 지문과 표시이름뿐.** 접속에 쓸 수 있는 것은 하나도 없습니다 |

그래서 **등재는 컨트롤 플레인이 대상을 지목하는 것이 아니라, 러너가 확인해서 올리는
것**입니다. 화면에서 하는 일은 "연결확인을 실행하라"는 지시 하나이고, 돌아오는 것은
지문·표시이름·성패입니다. 실패한 대상은 러너가 붙인 로컬 별칭으로 보고하므로
(*"web-01 — 인증 거부"*), 주소 없이도 운영자가 무엇이 안 붙었는지 압니다.

작업 지시도 주소가 필요 없습니다. 계약이 이미 `target_node_ids`로만 대상을 넘기게
되어 있고(`CollectRequest`), 그 식별자를 접속으로 푸는 것은 러너의 몫입니다.

**이렇게 두면 우리 DB가 털려도 고객 내부 주소 지도가 나오지 않습니다.** 내부 IP 대역과
포트 구성 자체가 정찰 정보라, 인벤토리와 함께 새면 피해가 배가됩니다.

엣지 해소도 **러너가 합니다.** 자기 조직의 대상 목록을 이미 갖고 있어 컨트롤 플레인보다 잘
풉니다. 등재된 상대는 `dst_node_id`로 해소되어 올라가므로 주소가 남지 않습니다.

### 6.3.1 주소를 올릴지는 고객이 정합니다

**주소를 지우는 것이 늘 좋은 것은 아닙니다.** 인벤토리 화면을 실제로 쓰는 사람에게는
`10.20.3.14:443`이 `node-7f3a`보다 알아보기 쉽고, 아직 등재되지 않은 통신 상대를
*"이것을 등재하시겠습니까"*로 물을 때도 주소가 있어야 판단이 빠릅니다. 운영 편의가
분명히 있는 자리입니다.

**그 편의와 반출 최소화 중 무엇을 고를지는 조직마다 다릅니다. 그래서 우리가 정하지 않고
러너 설정으로 뺍니다.**

```
PQCATON_EXPOSE_ADDR=off   # 기본값 — 주소를 올리지 않는다
                   on     # 올린다. 화면에서 IP·포트로 노드를 본다
```

| | `off` (기본) | `on` |
|---|---|---|
| 노드 주소 | 올리지 않습니다 | 올립니다 |
| 미등재 상대 | **결정론적 토큰**으로 치환 — `unknown-a1b2` | `ip:port` 그대로 |
| 화면에서 노드 식별 | 표시이름·FQDN·지문 | 주소까지 |
| 미등재 상대의 실제 주소 확인 | **러너 쪽에서** 봅니다 | 화면에서 |

**토큰으로 치환해도 구조는 그대로 보입니다.** 같은 주소는 항상 같은 토큰이 되므로,
*"이 미등재 상대 하나가 노드 일곱 개와 통신하고 있다"*가 그대로 드러납니다. 등재 판정에
필요한 것은 대개 그 구조이지 주소 자체가 아닙니다. 실제 주소가 필요한 순간에만 러너에서
풉니다.

이 방식은 [운영 문서의 「식별자 토큰화」](https://github.com/sntsoftgit/pqcaton-saas)가
적어 둔 것과 같은 메커니즘이고, 한계도 같습니다 — **엣지 구조·규모·시간 패턴으로 역추적할
여지는 남습니다.** 주소를 지운다고 익명이 되지는 않습니다.

**설정이 러너에 있다는 것이 핵심입니다.** 컨트롤 플레인에서 이 값을 바꿀 수 없습니다.
바꿀 수 있으면 그 약속은 우리가 언제든 깰 수 있는 것이 되고, 고객 보안팀이 검증할 대상이
아니라 우리를 믿어 달라는 말이 됩니다.

**`off`의 비용도 적어 둡니다** — 장애 지원 때 우리가 무엇을 보고 있는지 알기 어려워지고,
운영자가 러너에 접근할 수 있어야 실제 주소를 확인합니다. 그래서 기본값을 `off`로 두되
**전환을 쉽게** 하고, 화면에는 지금 어느 쪽인지를 항상 표시합니다 — 주소가 비어 있는 것이
"관측하지 못한 것"으로 읽히면 안 됩니다.

**왜 지문을 미리 확보하나**

| | |
|---|---|
| **접속 실패를 관측 전에 잡습니다** | 수백 대를 등록하면 방화벽·계정·권한 때문에 상당수가 붙지 않습니다. 관측을 다 돌린 뒤에 알면 그 시간이 버려집니다 |
| **과금이 예측 가능해집니다** | 운영자가 청구 전에 "이번 달 몇 노드인지"를 압니다. 청구서에서 처음 알게 되지 않습니다 |
| **회피가 등재 단계에서 드러납니다** | 접속 정보를 다른 서버로 돌리면 **다른 지문**이 올라옵니다. 관측까지 갈 것도 없이 새 노드로 세어집니다 |
| **무료 범위를 집행할 자리가 생깁니다** | 라이선스의 5노드 제한을 여기서 겁니다. 관측을 돌린 뒤에 거절하면 이미 남의 서버를 들여다본 뒤입니다 |

**지문이 겹치거나 어긋날 때** — VM을 클론하면 `machine-id`가 같아져 두 머신이 하나로 보이고,
재설치하면 같은 머신이 새 노드로 보입니다. 둘 다 **등재를 보류하고 운영자에게 확인을
요청합니다.** pqcota의 적재 단계가 사용자가 지정한 식별자와 실제 지문을 교차 검증해
불일치를 기록으로 남기므로(`CheckIdentity` → `pqcota_rejections`), 같은 판정을 등재
단계로 앞당기는 것입니다.

**등재되지 않은 상대가 관측에 걸리면** — 네트워크 관측은 등재되지 않은 통신 상대를 봅니다.
그것을 조용히 버리지 않고 **"등재 판정 요청"으로 띄웁니다.** 과금하지 않되 존재는 알립니다 —
조직이 모르던 연결이 바로 이 제품의 첫 값이기 때문입니다.

### 6.4 무엇으로 신뢰하나

두 층입니다.

| 층 | 무엇을 확인 | 없으면 |
|---|---|---|
| **러너 토큰** | 이 러너가 그 조직의 것인가 | 요청 거절 |
| **collector ed25519 서명** | 이 관측이 진짜 그 collector가 낸 것인가 | 결과 거절 — 기록은 남깁니다 |

**토큰만으로는 부족합니다.** 러너가 감염되면 토큰도 함께 넘어갑니다. collector 서명은 그 아래
층이라, 러너를 잡아도 관측을 위조하려면 collector 키가 따로 필요합니다. **그 층이 유지되는
조건이 §6.2입니다** — 키를 러너가 등록할 수 없어야 합니다.

서명은 새로 만들 것이 아닙니다 — pqcota가 `pqcota-keygen`으로 키쌍을 만들고
`PQCOTA_SIGN_KEY`로 서명하며, v0.2.0에서 검증 쪽도 갖췄습니다.

**우리가 만드는 것은 등록소 하나입니다.** `(조직, collector_id) → 공개키`. 그리고 확인할 때
**그 조직의 키만 좁혀서 넘깁니다.**

| | |
|---|---|
| 왜 좁혀야 하나 | `sign.Verify`는 넘긴 키를 **전부 시도**해 하나라도 맞으면 통과시킵니다. 전 조직 키를 한 목록으로 넘기면 조직 A의 collector가 서명한 결과가 B로 들어갑니다 |
| 무엇을 쓰나 | `sign.VerifyFrom(keys, res)` — `collector_id`로 키를 **찾아서** 그 키로만 확인합니다. 다른 collector_id를 달고 오는 것도 함께 막힙니다 |
| 검증을 못 하면 | 필수 모드(`RequireSignature`)에서 검증자가 없으면 적재 자체가 거절됩니다. **"확인 못 했다"는 "틀렸다"와 따로 셉니다**(`Unverified` vs `Rejected`) — 설정이 빠진 것과 위조가 같은 숫자에 묻히면 안 됩니다 |
| 거절한 것은 | `pqcota_rejections`에 사유와 함께 남깁니다. 조용히 버리면 러너가 잘못 설정된 것과 아무 일도 없던 것이 구분되지 않습니다 |

조직은 러너가 주장하는 것이 아니라 **토큰에서 유도합니다.** 결과 본문에 조직이 적혀 있어도
보지 않습니다.

#### 6.4.1 러너 토큰

**불투명 랜덤입니다. 서명 토큰(JWT 류)을 쓰지 않습니다.**

§6.4가 세운 전제가 *"러너가 감염되면 토큰도 함께 넘어간다"*입니다. 그러면 **즉시 폐기**가
요건인데, 서명 토큰은 만료 전까지 유효하고 폐기하려면 결국 폐기 목록을 매 요청 조회해야
합니다 — DB를 안 본다는 이점이 사라지고 서명 키 관리만 남습니다.

```
pqcrt_<조회키 8자>_<비밀 32자>          base32
```

| | |
|---|---|
| 접두어 | 로그에서 눈에 띄고 시크릿 스캐너에 걸립니다. 실수로 붙여 넣은 것을 찾을 수 있습니다 |
| 조회키 | **평문으로 저장**하고 인덱스를 겁니다. 해시 전체를 뒤지지 않고 한 번에 찾습니다 |
| 비밀 | **SHA-256으로 저장.** bcrypt·argon2를 쓰지 않습니다 — 고엔트로피 랜덤이라 사전공격 대상이 아니고, 매 요청 검증이라 느린 해시는 비용만 됩니다. 비교는 상수시간으로 합니다 |
| 평문 | **발급 순간에만 보여 줍니다.** 다시 못 봅니다 |

```
pqcaton_runner_token
    lookup         TEXT PRIMARY KEY     -- 토큰 앞부분(평문)
    org            TEXT NOT NULL
    zone           TEXT NOT NULL        -- 어느 영역의 러너인가(§6.2.2)
    secret_sha256  BYTEA NOT NULL
    label          TEXT                 -- "본사 러너", "DR 센터"
    issued_at      TIMESTAMPTZ NOT NULL DEFAULT now()
    last_used_at   TIMESTAMPTZ
    revoked_at     TIMESTAMPTZ          -- NULL이면 유효
```

**만료를 두지 않습니다.** 러너는 상주 프로세스라 만료는 장애로만 나타납니다. 대신 폐기와
`last_used_at`을 둡니다 — 오래 안 쓰인 토큰을 찾아 거둘 수 있습니다.

**조직당 여러 개 발급합니다. 영역마다 하나씩입니다**(§6.2.2). 하나를 폐기해도 다른 영역의
러너는 계속 돌아야 합니다. 러너가 어느 토큰으로 등록했는지 남기므로, 폐기하면 **그 토큰을 쓴 러너만** 끊깁니다.

```
pqcaton_runner
    id             TEXT PRIMARY KEY     -- 우리가 발급
    org            TEXT NOT NULL
    zone           TEXT NOT NULL        -- 토큰이 정합니다. 러너가 주장하지 않습니다
    token_lookup   TEXT NOT NULL        -- 어느 토큰으로 등록했나
    label          TEXT
    version        TEXT
    registered_at  TIMESTAMPTZ NOT NULL DEFAULT now()
    last_seen_at   TIMESTAMPTZ
```

발급은 **관리자 콘솔에서만** 합니다. 러너가 닿는 어떤 엔드포인트로도 토큰을 만들 수
없습니다 — 만들 수 있으면 토큰 하나로 토큰을 늘릴 수 있습니다.

#### 6.4.2 collector 공개키 등록소

```
pqcaton_collector_key
    org            TEXT NOT NULL
    collector_id   TEXT NOT NULL
    public_key     TEXT NOT NULL        -- base64 ed25519
    label          TEXT
    registered_at  TIMESTAMPTZ NOT NULL DEFAULT now()
    revoked_at     TIMESTAMPTZ          -- NULL이면 유효
    PRIMARY KEY (org, collector_id, public_key)
```

**기본키에 `public_key`가 들어가는 것이 요점입니다.** 같은 `(조직, collector_id)`에 유효한
키가 **둘 이상인 구간**이 필요합니다 — 새 키를 등록하고, 러너들이 갈아탄 뒤, 옛 키를
폐기합니다. 그 구간이 없으면 키를 바꾸는 순간 그 조직의 관측이 전부 거절됩니다.

**그래서 `sign.VerifyFrom`을 쓰지 않습니다.** 그 함수는 `collector_id → 공개키` 하나만
받아 교체 구간을 표현할 수 없습니다. 대신 이렇게 합니다.

```sql
SELECT public_key FROM pqcaton_collector_key
 WHERE org = $1 AND collector_id = $2 AND revoked_at IS NULL
```

이 목록을 `sign.Verify`에 넘깁니다. **안전성은 같습니다** — `VerifyFrom`도 결국 엔벨로프의
`collector_id`로 키를 찾고, 우리는 그 좁히는 일을 질의로 할 뿐입니다. 대신 조직 조건이
질의에 함께 붙어 조직 경계도 같은 자리에서 걸립니다.

**등록도 관리자 콘솔에서만** 합니다(§6.2).

#### 6.4.3 선언된 엣지 귀속 — 이력은 우리 몫입니다

pqcota v0.4.0이 `pqcota_edge_attribution`을 냈습니다. 관측이 못 잡은 엣지의 앱 귀속을
사람이 선언으로 메우는 자리이고, 조직 축도 처음부터 들어가 있습니다.

**그 테이블은 덮어쓰기입니다** — 같은 `(org, node_id, dst)`에 다시 선언하면 이전 값이
사라집니다. 상류에서는 맞는 결정입니다. 선언은 사람이 고치는 설정이고, pqcota는 관측 도구라
거버넌스를 하지 않습니다.

**호스팅에서는 그대로 두면 안 됩니다.** 이 선언은 *"이 통신은 저 앱의 것이다"*라는 **사람의
판단**이고, 그 판단으로 조치 대상이 바뀝니다. 누가 언제 무엇을 무엇으로 바꿨는지가 남지
않으면, 사고 뒤에 *"왜 이 엣지가 저 앱으로 잡혀 있었나"*에 답할 수 없습니다.

그건 상류 결함이 아니라 **우리가 할 일입니다** — 이 리포가 존재하는 이유가 판정을 남기는
것입니다([docs/design.md §1.5](../docs/design.md)). 선언 귀속을 화면으로 열 때 **판정
저장소와 같은 append-only 이력**을 함께 남깁니다. 상류 테이블은 현재 값을, 우리 이력은
누가 언제 바꿨는지를 답합니다.

### 6.5 중복과 순서

같은 결과가 두 번 올 수 있습니다 — 러너가 올린 뒤 응답을 못 받고 재시도하는 경우입니다.
**인벤토리가 append-only라 중복이 이력을 망가뜨리지는 않지만**, 같은 관측이 두 번 쌓이면
"언제 봤나"가 틀어집니다.

**멱등 키는 `sign.Canonical`의 해시입니다.** 서명 대상 바이트를 그대로 해시합니다. 같은 키가
다시 오면 새로 쌓지 않고 받았다고만 답합니다.

엔벨로프의 `collector_id`+`target_node_id`+수집 시각을 키로 삼지 않습니다. `CollectionResult`는
**노드당 여러 개**가 나올 수 있어서(JVM마다 하나) 그 셋이 같은 결과가 정상적으로 생깁니다 —
서로를 중복으로 접어 조용히 버리게 됩니다.

canonical 해시는 그 문제가 없습니다. 서명이 `raw_capture`와 CBOM 본문까지 덮으므로 **다른
관측은 다른 해시**가 나오고, 재전송만 같은 해시가 됩니다. 새로 계산할 것도 없습니다 — 어차피
서명을 확인하려고 만드는 바이트입니다.

> **전제 하나** — 이 키는 `collected_at`이 채워져 있어야 성립합니다. 비어 있으면 상태가 그대로인
> 대상을 **다시 관측**했을 때 바이트가 완전히 같아져서, 재관측이 재전송으로 접힙니다. 그러면
> `pqcota_observations`가 지키는 "언제·몇 번 봤나"가 사라집니다. v0.1.3에서 collector 전부가
> 채우도록 고쳐졌습니다.

두 층이 겹치지 않습니다 — **canonical 해시가 재전송을 접고, 스냅샷의 `content_hash`가 변화
없는 상태를 접습니다.**

### 6.6 버전이 어긋날 때

러너는 자동으로 갱신되지만 즉시는 아닙니다. **옛 러너가 새 컨트롤 플레인에 붙는 구간이 늘 있습니다.**

- 계약(`contracts/`)이 순수 additive로만 바뀌므로 옛 러너가 보낸 것은 그대로 읽힙니다
- 컨트롤 플레인이 옛 러너가 모르는 작업을 주지 않습니다 — `register`에서 받은 러너 버전으로 거릅니다
- 너무 오래된 러너는 갱신을 요구하고 작업을 주지 않습니다. **그 사실을 상태로 남깁니다** — 조용히
  일을 안 하면 "관측할 것이 없다"로 읽힙니다

#### 읽히는 것과 검증되는 것은 다릅니다

**계약이 additive여도 서명은 깨집니다.** pqcota v0.3.0이 엣지를 앱에 귀속시키며
`sign.Canonical`의 엣지 부분에 `app_key`·`app_key_kind`를 더했습니다. 필드가 는 것은
additive지만, **서명 대상 바이트가 달라집니다.**

| | |
|---|---|
| 옛 collector가 서명한 것 | 그 두 필드가 **없는** 바이트열 |
| 새 코드가 계산하는 것 | 두 필드가 **빈 값으로 들어간** 바이트열 |

→ 옛 collector의 결과를 새 컨트롤 플레인이 검증하면 **실패합니다.** 우리는 검증을 필수로
두기로 했으므로 그 결과는 거절되고 `pqcota_rejections`에만 쌓입니다.

**엣지가 없는 결과는 영향이 없습니다** — `edgeCanon`이 불리지 않기 때문입니다. 즉
openssl·JVM 관측은 버전이 섞여도 통과하고, **네트워크 관측만 끊깁니다.** 하필 UNDECLARED
엣지가 이 제품의 첫 값이라, 조용히 두면 *"통신이 관측되지 않았다"*로 읽힙니다.

**그래서 이렇게 합니다.**

| | |
|---|---|
| 서명 범위가 바뀌는 릴리스는 | collector와 컨트롤 플레인을 **함께 올립니다.** 러너 자동 갱신이 끝나기 전에 컨트롤 플레인만 올리지 않습니다 |
| 애초에 오지 않게 | **옛 러너에게 관측 작업을 주지 않습니다.** §6.6의 "너무 오래된 러너는 갱신을 요구하고 작업을 주지 않는다"가 그 장치입니다 — 사후에 분류하는 것보다 안 오게 하는 편이 확실합니다 |
| 그래도 오는 것은 | 거절하고 **러너 버전과 엣지 유무를 함께 기록**합니다. *"이 러너의 엣지 결과만 전부 실패"*라는 모양이 보이면 운영자가 갱신 문제임을 압니다 |

> **거절 사유만으로는 구분할 수 없습니다.** `Envelope.collector_version`이 `"0.1.0"`으로
> **하드코딩된 상수**라 pqcota 릴리스를 따라가지 않습니다 — 그 값으로는 옛 형식인지
> 위조인지 가릴 근거가 없습니다. 그래서 **분류가 아니라 예방**에 기댑니다. 상류가
> 서명 규격 버전을 엔벨로프에 넣어 주면 그때 진짜로 구분됩니다.
| 운영자에게는 | 그 조직의 화면에 **"이 노드들의 네트워크 관측이 collector 버전 때문에 들어오지 않고 있습니다"**를 띄웁니다 |

> **상류에 제안할 것** — `Envelope`에 서명 규격 버전을 두면 검증 측이 그 버전의 canonical로
> 계산할 수 있습니다. 지금은 최신 형식 하나만 있어 옛 서명을 확인할 방법이 없습니다.
> 대회 마감(2026-08-27) 뒤에 올릴 항목입니다.

### 6.7 수신 API가 한 겹 더 보는 것

§4에서 적었듯 `raw_capture`를 막는 것은 타입이 아니라 규약입니다. 규약은 깨질 수 있으므로
경계에서 한 번 더 봅니다.

| 무엇 | 어떻게 |
|---|---|
| `raw_format`이 아는 값인가 | 알려진 형식 목록과 대조합니다. **닫힌 목록으로 계약에 박지는 않습니다** — pqcota는 제3자 CBOM 도구 위임을 설계로 열어 두었고, 닫으면 그 확장점이 막힙니다. 목록은 우리 정책으로 들고 있다가 새 형식이 오면 넓힙니다 |
| 본문이 지나치게 큰가 | **자르지 않고 거절합니다.** 잘라내면 증거가 조용히 사라집니다 — 이 제품이 가장 피하는 일입니다. 거절은 사유와 함께 남으므로 무엇이 왜 안 들어왔는지가 보입니다 |

**자르지 않고 거절한다**가 이 절의 요점입니다. 받아서 훼손하느니 안 받고 그 사실을 남깁니다.

### 6.8 지금 없는 것

이 절 전부입니다. 설계이고 구현은 없습니다. 적재 쪽 재료(서명 필수 모드·`VerifyFrom`·거절
이력·조직 축)는 pqcota v0.2.0에 있으므로, 남은 것은 **그것을 부르는 HTTP 경계와 등록소**입니다.

## 7. 이식성 — 깨지 않아야 할 것

컨트롤 플레인은 **컨테이너 + 관리형 PostgreSQL + S3 호환 스토리지**만 씁니다. 제공사 전용
서비스(전용 서버리스·큐·인증·워크플로)를 쓰지 않습니다.

이유는 취향이 아닙니다. **어디서 돌릴지가 고객마다 다릅니다** — 우리 호스팅, 고객이 지정한
클라우드, 고객 자기 환경. 셋 다 같은 컨테이너여야 합니다. 그때 며칠 안에 세울 수 있어야
그 요구를 받습니다.

**지금 코드가 이미 그 조건을 만족합니다** — Go 정적 바이너리와 `pgxpool`뿐, 클라우드 SDK가 하나도
없습니다. 지키는 것이 만드는 것보다 쉽습니다.
