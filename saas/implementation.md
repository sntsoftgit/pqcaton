# 구현 순서 — 컨트롤 플레인

[design.md §6](design.md)의 프로토콜을 무엇부터 만들지 정합니다. 설계는 그쪽에 있고,
여기는 **순서와 그 이유**만 적습니다.

> **왜 지금인가** — 네이버 클라우드 제휴 절차 ③이 **NCP 위에서의 구성·기능·성능 검증(PoC)**
> 입니다. 통과 통보를 받고 시작하면 그 일정에 끌려갑니다.

## 배포 형태 — 유료는 전용, 무료는 공용

**유료 고객은 고객마다 컨트롤 플레인 하나**, **무료 고객은 전부 한 인스턴스**를 씁니다
([design.md §1](design.md)). 이 리포에 미치는 영향은 작지만, 두 가지가 달라집니다.

| | |
|---|---|
| **조직 격리는 실제로 쓰입니다** | 무료 인스턴스가 여러 조직을 한 DB에 담습니다. `CP-ORG-1`·`CP-PG-8`이 재는 것이 거기서 그대로 운영 성질이 됩니다 — 「나중을 위한 방어선」이 아닙니다 |
| **DSN은 하나입니다** | 인스턴스마다 DB 하나라 조직별 DSN 매핑이 필요 없습니다. 조직마다 히스토리 핸들을 여는 자리([main.go](cmd/pqcaton-api/main.go)의 `stores`)는 무료 인스턴스 때문에 **그대로 필요합니다** |

**전용 인스턴스라고 org를 지우지 않습니다.** 지우면 무료 인스턴스가 못 돌고, 계열사를 한
인스턴스에 담는 요구도 흔합니다. 값은 이미 치렀고 유지 비용은 없습니다.

## 어디에 두나

`pkg/`는 호스팅을 모릅니다([README](README.md#왜-별도-폴더인가)). 그래서 컨트롤 플레인
코드는 `saas/` 아래 둡니다.

```
saas/cmd/pqcaton-api/      수신 API 서버
saas/internal/...          토큰·등록소·작업 큐·핸들러
```

`pkg/inventory/*`와 pqcota의 계약은 **부르기만 합니다.** 반대 방향은 없습니다.

## 먼저 정할 것 둘

### ① `org.ID`가 두 개입니다

v0.2.0으로 pqcota에도 `pkg/org`가 생겨, 지금 두 리포에 **서로 다른 `org.ID` 타입**이
있습니다. 컨트롤 플레인은 둘 다 쥐게 됩니다 — 판정 저장소는 pqcaton 것에, 인벤토리
저장소는 pqcota 것에 묶입니다.

| | pqcaton `pkg/org` | pqcota `pkg/org` (v0.2.0) |
|---|---|---|
| 빈 조직 | `Parse`가 **거절** | `Resolve`가 **`default`로 품** |
| 기능 | `Parse` 하나 | `Parse` · `Resolve` · `Required` · `Scoped` · `Default` |

**같은 문자열이 두 경로에서 다르게 처리됩니다.** 그대로 두면 경계마다 변환이 생기고,
검증 규칙이 어느 쪽인지 헷갈리는 자리가 남습니다.

**pqcota의 것으로 모았습니다**(`4b09d4c`). 상류이고 상위집합입니다. 다만 **`Resolve`는 쓰지
않습니다** — 토큰에서 유도한 조직이 비어 있는 상황은 품을 것이 아니라 버그입니다.
pqcaton의 "빈 조직은 열 수 없다"는 규칙은 그렇게 지킵니다.

### ② 등재(`enroll`)를 먼저 만들지

논리로는 등재가 앞섭니다 — 관측은 등재된 노드에만 갑니다([design.md §6.3](design.md)).
그런데 **만드는 순서로는 결과 수신이 먼저입니다.**

등재도 결국 같은 것 위에 올라갑니다 — 토큰에서 조직을 유도하고, HTTP 경계를 지나,
저장소에 씁니다. **그 경계를 완성시키는 것이 결과 수신 경로**이고, 등재는 그 위의 얇은
작업 하나입니다. 반대로 등재부터 만들면 경계가 절반만 선 채로 두 번 손대게 됩니다.

## 마일스톤

| | 무엇 | 끝나면 증명되는 것 |
|---|---|---|
| ~~**M0**~~ | **끝났습니다.** 조직·토큰 경계 — `org` 통합 · 러너 토큰 발급/검증 · **collector 공개키 등록소**(관리자 경로). 토큰 형식과 테이블은 [design.md §6.4.1·§6.4.2](design.md) | 조직이 토큰에서 유도되고, 러너는 자기 조직을 주장할 수 없습니다 |
| ~~**M1**~~ | `POST /v1/runner/results` — 서명 확인 → 조직 부여 → 적재 | **끝났습니다.** `saas/internal/{intake,api}` · `saas/cmd/pqcaton-api` |
| **M2** | **거의 됐습니다** — 작업 저장소(인메모리·Postgres) · 만료·재배포 정책 · `GET /v1/runner/jobs` 롱폴 · 배경 정리자 · **결과로 작업 닫기**. **남은 것: 종류별 점유 만료 · 옛 러너 거르기(§6.6)** | 컨트롤 플레인이 러너를 부릴 수 있습니다 |
| **M3** | `enroll` — 등재 · 지문 충돌 보류 · 월중 고유 노드 카운터 · **영역**(§6.2.2) | 과금과 무료 5노드 집행이 붙고, **작업이 닿는 영역에만 나갑니다** |
| **M4** | `observe` — collector 반입·실행·회수 | **러너 왕복이 완성됩니다.** PoC에서 보여 줄 것이 여기까지입니다 |
| **M4+** | **영역 간 엣지 해소** — 미해소 상대를 조직 전체의 등재 정보로 이어 붙입니다(§6.3.1) | 영역을 넘는 통신이 「모르는 상대」로 남지 않습니다 |
| **M5** | `POST /register` · `POST /status` | 버전 관리와 살아있음 |
| **M6** | 사용자 인증 · 관리 화면 | 사람이 쓰는 물건이 됩니다 |

**PoC 최소선은 M4까지**입니다. M6은 검증 항목이 아니지만, 없으면 보여 줄 화면이 없으니
M4 다음에 최소 화면을 붙입니다.

### M1을 가장 앞에 두는 이유

만들 것이 가장 적고 값이 가장 컸습니다. pqcota가 이미 갖춘 것을 부르기만 합니다.

| 필요한 것 | 어디 있나 |
|---|---|
| 서명 검증 | `sign.Verify(keys, res)` — 등록소가 `(조직, collector)`로 좁힌 키만 넘깁니다. `VerifyFrom`은 collector당 키 하나만 받아 **교체 구간을 표현하지 못합니다**(§6.4.2) |
| 검증 필수화 | `ingest` 옵션 `RequireSignature` |
| 거절·미검증 기록 | `pqcota_rejections` |
| 조직 격리 저장 | `history.NewPgStoreIn(ctx, dsn, org)` |

**우리가 새로 쓰는 것은 HTTP 핸들러와 등록소 조회뿐입니다.**

## 각 마일스톤에서 놓치기 쉬운 것

| | |
|---|---|
| M0 | 공개키 등록은 **러너가 닿는 어떤 경로로도 열지 않습니다**([design.md §6.2](design.md)). 열면 2층 방어가 1층이 됩니다 |
| M1 | 멱등 키는 `sign.Canonical`의 해시입니다. 엔벨로프 삼중키를 쓰면 노드당 결과가 여럿일 때 정상 결과끼리 서로를 접습니다 |
| M1 | 본문 크기 초과는 **자르지 않고 거절**하고 사유를 남깁니다 |
| M1 | 거절된 결과를 **「본 것」으로 남기지 않습니다.** 남기면 키를 뒤늦게 등록해도 중복으로 접혀 영영 못 들어옵니다 — 멱등은 재전송을 접는 장치이지 실패를 굳히는 장치가 아닙니다 |
| M2 | v0.3.0이 서명 범위를 넓혀 옛 collector의 엣지 결과는 검증에 실패합니다. **분류로는 못 가립니다**(`collector_version`이 상수) — **옛 러너에게 작업을 주지 않는 것**이 대응입니다([design.md §6.6](design.md)) |
| M6 | 선언 엣지 귀속을 화면에 열면 **누가 언제 바꿨는지를 우리가 남깁니다** — 상류 테이블은 덮어쓰기입니다([design.md §6.4.3](design.md)) |
| M2 | `provision` 작업의 재배포는 `observe`와 다릅니다 — 두 번 적용될 수 있습니다 |
| M2 | 작업은 **결과로 닫습니다**([design.md §6.2.1](design.md)). 못 닫아도 결과는 버리지 않습니다 — 어긋난 것이 작업 id 하나인데 관측 전체를 잃습니다 |
| M2 | `runner_id`는 아직 **러너가 스스로 대는 값**입니다. 토큰이 조직 단위라 유도할 수 없습니다 — 같은 조직 안에서는 서로의 작업을 닫을 수 있습니다. `register`(M5)가 닫습니다 |
| M3 | 등재 실패는 과금하지 않습니다. 등재 **후** 지속 실패는 아직 정하지 않았습니다(알림 + 보류 제안이 유력) |
| M3 | **등재가 노드를 영역에 넣습니다**([design.md §6.2.2](design.md)). 지금은 그 자리가 없어 `Lease`가 조직만 보고 주므로 **DR 작업을 본사 러너가 가져갑니다.** 상류에는 영역이 없고(proto에 `runner`·`org` 0건) 넣을 것도 아닙니다 — **영역은 배포 축이지 관측 사실이 아닙니다.** `(org, node_id) → zone` 한 장을 우리 테이블에 두고 `node_id`로 잇습니다. 대상이 여러 영역에 걸치는 작업은 **만들 때 쪼갭니다** — 한 작업이 두 영역을 필요로 하면 어느 쪽도 완결하지 못합니다 |
| M5 | `access.Runner`·`TouchRunner`가 **조직을 묻지 않습니다**(`WHERE id=$1`뿐). 러너 id를 우리가 발급해 전역 유일이라 지금 새지는 않지만, "조직 없이 열리는 경로를 하나도 두지 않는다"(CP-JOB-9·CP-KEY-6)에서 이 둘만 빠져 있습니다. `register`가 쓰기 시작하기 전에 맞추는 편이 쌉니다 |
| M4 | 접속 정보는 컨트롤 플레인에 올라오지 않습니다. 작업 지시는 `target_node_ids`로만 합니다 |
| M3 | **등재가 주소 토큰도 올려야 합니다**([design.md §6.3.1](design.md)). 없으면 영역 간 엣지를 이어 붙일 표가 생기지 않습니다 — 나중에 만들려면 전 노드를 다시 등재해야 합니다. **토큰화 키는 조직 단위**여야 하고, 러너마다 다르면 같은 주소가 영역마다 다른 토큰이 되어 영영 못 맞춥니다 |
| 배포 | **`PQCOTA_REQUIRE_ORG=1`을 켜는 자리가 아직 없습니다.** 무료 인스턴스는 여러 조직을 한 DB에 담으므로, 조직 없이 저장소를 여는 호출이 있으면 상류 기본 조직(`default`)에 조용히 쌓입니다. 지금은 토큰에서 유도한 값을 넘겨 그럴 일이 없지만, 스위치는 **데이터가 섞이기 전에** 켜 두는 것입니다 |

## 지금 만들지 않는 것

| | 왜 |
|---|---|
| 프로비저닝 배포 | 확정 계획이 있어야 나옵니다. 관측 왕복이 먼저입니다 |
| 정책 상속·대규모 일괄 | 설계만 있습니다([docs/design.md §1.6](../docs/design.md)). 없는 기능을 상품에 넣지 않기로 했습니다 |

| 고객 키 암호화·토큰화 | 요구하는 고객이 나타난 뒤에 정합니다 |

## 다음에 손댈 자리

**점유 만료를 작업 종류가 정하지 않습니다**([design.md §6.2.1](design.md)이 정하라고
적어 둔 것입니다). 지금은 `api.DefaultJobLease` 10분 하나입니다 — 관측은 대상 수에 비례해
길어지고 적용은 플레이북에 달렸는데, 한 값으로 둘을 다 덮고 있습니다. 짧으면 멀쩡히 도는
작업을 뺏고, 길면 죽은 러너의 작업이 그만큼 묶입니다.

**연장 경로가 없어 10분이 사실상 상한입니다.** 진행 중 알림은 `POST /v1/runner/status`에
얹기로 했고(엔드포인트 넷을 지킵니다), 그 엔드포인트가 M5입니다. 그때까지는 종류별 값이
곧 상한입니다.

1. `Kind`가 만료를 정한다 — `Store.Lease`가 `till`을 미리 받는 구조라 서명을 바꿔야 합니다.
   부르는 쪽은 **어떤 종류가 나올지 모른 채** `till`을 정하고 있습니다
2. **옛 러너 거르기**(§6.6) — 배포 전에 러너 버전을 봅니다. 서명 범위가 넓어진 뒤로 옛
   collector의 엣지 결과는 검증에 실패하고 **분류로는 못 가립니다**. 거를 때 그 사실을
   남겨야 합니다 — 조용히 안 주면 "관측할 것이 없다"로 읽힙니다. 러너 버전은 `register`
   (M5)에서 저장하므로 그 자리와 함께 정합니다

**작업을 만드는 자리는 아직 없습니다.** `Put`을 부르는 것은 테스트뿐입니다 — 받아 갈 수는
있는데 넣는 쪽이 없습니다. 종류별 생성은 M3(등재)·M4(관측)의 몫이라 그쪽에 붙입니다.

## 상류 의존

`go.mod`가 pqcota `v0.4.0`에 고정돼 있고, 모듈 경로가 리포 주소와 달라 `replace`가 붙어
있습니다. 상류가 대회 마감(2026-08-27) 뒤에 경로를 정리하면 그 줄을 지웁니다.
**그때까지 상류에 새 요구를 넣지 않습니다** — M0~M4는 v0.4.0으로 전부 됩니다.

마감 뒤에 올릴 것은 하나입니다 — **`Envelope`에 서명 규격 버전.** 지금은 최신 canonical
형식 하나뿐이라 옛 서명을 확인할 방법이 없습니다(§6.6).
